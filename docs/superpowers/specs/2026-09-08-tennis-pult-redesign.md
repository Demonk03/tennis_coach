# AI Tennis Coach: «Пульт» — согласованные требования к реализации

Дата: 2026-09-08. Статус: решения собраны в интервью; документ подготовлен для итогового просмотра пользователем. Реализация не начата.

## 1. Назначение и приоритет требований

Переработать личный мобильный PWA-тренер по макету «Пульт», сохранив существующие матчи, их идентификаторы, анкеты, планы, наблюдения, советы, результаты и разборы. Главный сценарий — быстро отметить проблему на переходе, получить и прочитать применимый совет.

Этот документ имеет приоритет над противоречащими ему указаниями в `design_handoff_tennis_1c/README.md`. HTML-файлы в этой папке — визуальные референсы, а не код для переноса в приложение. `support.js` в продакшен не переносить.

Сохраняется стек: статический `docs/` (vanilla JS и CSS без сборки), Flask API, Supabase, OpenAI. Допускаются необходимые изменения backend, промптов, API и аддитивные миграции БД. Существующие API-контракты сохраняются для старых клиентов, новые возможности добавляются явно.

Сохраняются характер макета, палитра, шрифты, композиция карточек и ручная светлая/ночная тема. Пиксельное совпадение не требуется: размеры, расположение и подписи можно менять ради читаемости, доступности и меньшего числа действий.

## 2. Решения пользователя

| Редактирование подготовки | До старта можно изменить анкету и пересобрать план в том же матче |
| После старта | Исходная анкета и план неизменны; новые данные — через переход и новый сет |

| Готовый разбор | Не редактируется и повторно не генерируется |

Оставшиеся технические детали ниже — принятые проектные решения для реализации этих требований, а не дополнительные функции, запрошенные пользователем.

## 3. Жизненный цикл и навигация

Одновременно существует не более одного матча `preparing` или `in_progress`.

| Состояние данных | Экран при восстановлении / открытии |
|---|---|
| Нет настроенного подключения | Настройки |
| Нет активного матча | Подготовка с локальным черновиком, если он есть |
| `preparing` | Сохранённый план с действиями «На корт» и «Изменить»; черновик правок предлагается продолжить отдельно |
| `in_progress` | Экран матча; последний совет из сохранённых событий |
| `completed`, нет review | Детали матча с действием «Разобрать матч» |
| `completed`, есть review | Детали и сохранённый разбор |
| Ошибка загрузки | Ошибка с повтором, а не ложное состояние «Матча нет» |

Основные разделы: Подготовка, Матч, Журнал, Профиль, Настройки. Вложенные экраны сохраняют понятный возврат в соответствующий сценарий. Переключение раздела не отправляет форму и не теряет черновик. Возврат из деталей сохраняет период, поиск и положение списка журнала.

При активном матче вкладка подготовки показывает его подготовку, а не анкету создания второго матча. После старта подготовка доступна только для чтения. Не показывать кнопку старта для уже начатого матча.

Отмена активного матча остаётся отдельным действием с подтверждением рядом с завершением; переводит в `cancelled`, не удаляет данные. Существующий отдельный механизм окончательного удаления завершённого матча не вызывается редизайном или миграцией автоматически; если сохраняется в UI, остаётся второстепенным действием с явным подтверждением.

Восстановление не должно незаметно переключать пользователя со свежего локального черновика на другой матч. Черновики привязаны к матчу и типу формы.

## 4. Подготовка и изменение плана

Сохраняются поля существующей подготовки: одиночка/пара, покрытие, логин соперника (необязательно), уровень соперника, свободный стиль, событие, длительность сессии, погода, энергия 1–5, еда, состояние тела, настрой. Тип сессии и длительность остаются независимыми полями.

Поиск соперника предлагает существующие `opponent_name`; можно выбрать запись или ввести новый логин. Для поиска допустимо нечувствительное к регистру сопоставление, но выбранное сохранённое значение передаётся точно. У нового ввода убираются только крайние пробелы. Автоматическое объединение, исправление логинов и переименование старых записей не выполняются. Старые имена остаются доступны как есть. Пустое имя не создаёт общего «неизвестного соперника» и досье.

Карточка соперника не блокирует анкету при загрузке или ошибке. Для незнакомого соперника — честное пустое состояние. Не выводить вымышленное время матча или признаки вроде «лига», которых нет в данных.

Первое получение плана создаёт один `preparing`-матч после успешной генерации. Изменение существующей подготовки:

1. «Изменить» заполняет анкету сохранёнными данными этого матча либо предлагает продолжить его локальный черновик.
2. «Обновить план» генерирует план по изменённой анкете; прежняя версия остаётся рабочей до успеха.
3. После успеха контекст матча, анкета, снимок текущего профиля, структурированный план и legacy-тексты обновляются вместе, с тем же `match_id`.
4. Сбой генерации или записи не оставляет смесь старой анкеты и нового плана. Правки сохраняются локально; можно повторить или вернуться к прежнему плану.
5. Backend повторно проверяет `preparing` при записи. Конкурирующий старт или обновление возвращает конфликт; после старта никакая задержавшаяся генерация не меняет подготовку.

Для этого нужна атомарная серверная операция, например транзакционная Supabase RPC; последовательные независимые записи без отката не подходят. Использовать проверку ревизии подготовки для параллельных вкладок.

Для новых подготовок сохраняется также `match_context_snapshot` — контекст анкеты, находящийся сейчас в `matches` (соперник, уровень, исходный стиль, покрытие, событие, длительность, погода и тип матча). При пересборке до старта снимок обновляется атомарно с планом. После старта оба снимка и план неизменны даже при последующем изменении постоянного профиля.

Legacy `PATCH /api/matches/:id/opponent-style` сохраняется: уточнение после старта записывается отдельным датированным наблюдением контекста, а не в исходную анкету. Ответ и legacy-представление bundle могут показывать последний уточнённый стиль как `match.opponent_style`, но новый UI читает исходную анкету из снимка и отдельно показывает уточнение в истории. Новые промпты явно различают исходный контекст и уточнения. Для старого матча без снимка показываются имеющиеся поля с пометкой, что исходное значение могло уточняться; неизвестный стиль на момент старта не восстанавливается выдуманным backfill. Новый UI не использует этот PATCH: пользователь добавляет наблюдения через переход и новый сет.

План: фокус, три ориентира, тело, reset, соперник. Для старого неструктурированного плана — два существующих текстовых блока. Не обрезать рекомендации ради размеров примера в макете.

## 5. Матч, переход и новый сет

До первого совета на экране матча главным остаётся исходный фокус. После первого совета главным становится `generated_advice` последнего сохранённого события. Предматчевый план доступен ниже в раскрывающемся блоке. Тип и время совета позволяют отличить план нового сета от совета на переходе.

Точный текущий счёт и подающий не запрашиваются. Новый UI не вызывает обновление точного счёта. Старый `current_score` сохраняется как историческое поле, но не трактуется как актуальный контекст новых событий. В новые запросы модели он не попадает как свежий счёт; у новых событий без точного ввода `score_at_event = {}`. Старые события и их точный счёт не переписываются.

Номер текущего сета не показывается: количество запросов «Новый сет» не равно числу сыгранных сетов. Выдумывать номер по событиям нельзя. Шапка использует соперника и тип сценария.

### Переход

Две колонки с независимым мультивыбором:

| API key: свои наблюдения | Текст |
|---|---|
| `many_errors` | Много ошибок |
| `overhitting` | Рискую |
| `short_balls` | Коротко играю |
| `slow_movement` | Не двигаюсь |
| `tight` | Зажался |
| `emotionally_drained` | Морально устал |

`short_balls` означает недостаточную глубину, а не попадание в сетку. Ключи сохраняются. Соперник: Режет, Укорачивает, Возвращает всё, Давит с задней, Плоско, К сетке — с существующими API-ключами.

Положение: «Веду / Ровно / Проигрываю» (`ahead/even/behind`) именно в текущем сете. Стадия: начало / середина / концовка. На форме эти поля обязательны; при новой форме без черновика нет вымышленного выбранного ответа. Выбор «Как идёт» на главном экране, если он сохранён в компоновке, является черновиком следующего перехода и переносится в форму, но не создаёт событие сам по себе. Сохранённый прошлый статус подписывается как отметка на последнем переходе.

Нужен хотя бы один чип или непустой комментарий. Комментарий необязателен и раскрывается по нажатию. Кнопки возврата и «Один совет» закреплены над нижней навигацией с учётом клавиатуры и safe area.

### Новый сет

Общая визуальная структура с переходом, но отдельная семантика:

- Наблюдения относятся к только что законченному сету.
- Вместо относительного счёта — обязательный выбор «Выиграл сет / Проиграл сет».
- Стадия сета не спрашивается: предыдущий сет завершён.
- Обязательный запас сил 1–5, без скрытого вымышленного значения.
- Чипы / комментарий описывают законченный сет, как минимум одно наблюдение.
- Основное действие называется «План на сет»; результат — план следующего сета.

В API сохранять явный `completed_set_result` (`won/lost`), а не подменять результат относительным счётом нового сета. Старый формат `new_set` продолжает приниматься, но его `score_state` не преобразуется задним числом в результат сета. Промпт различает оба формата.

### Выдача

Отдельный экран с крупным текстом и кнопкой «На корт». Обычный совет сохраняет действующий лимит до 320 символов, новый сет — до 700. Компоновка проверяется на максимальных длинах, без обрезки содержимого. Дополнительный блок «Ты отметил» содержит исходные наблюдения; клиент не сочиняет причинное объяснение от имени AI.

## 6. Завершение и разбор

Итоговый счёт вводится текущими колёсами, похожими на iOS picker: мой / соперника, строки сетов, добавление и удаление последней строки (1–5 строк). Сохранить текущий диапазон колёс 0–12 с расширением до большего уже загруженного значения и формат строки `6-4 3-6 7-5`. Не заменять колёса степперами. Тестировать вертикальный жест без случайной прокрутки всей страницы и предусмотреть доступное управление без жеста.

Новый сценарий не включает завершение по времени с недоигранным сетом. Пустые добавленные строки не превращаются в результат; `0-0`, равный счёт сета и неопределённый победитель всего матча требуют исправления перед завершением. Сеты `6-0` и `0-6` допустимы. Не вводить жёсткое ограничение «ровно 6 геймов» или best-of-3: сохраняются привычные числовые результаты и возможный решающий тай-брейк. Парсер старых строк работает независимо и не переписывает старые данные.

Исход рассчитывается по числу выигранных сетов. Два действия: «Завершить и разобрать» и «Сохранить, разобрать позже». Оба сначала сохраняют `completed` и результат; только первое открывает анкету. Если разбор позже не удался, результат остаётся сохранённым. Повтор завершения после сетевого сбоя сверяется с сервером и не создаёт матч заново.

Анкета разбора:

- Физическое состояние 1–5 и психологическое состояние 1–5: обязательный явный выбор пятью кнопками, без скрытой подстановки 3.
- Свои ошибки (`own_errors`).
- Эмоции и концентрация (`emotional_state`).
- Стиль соперника: мультивыбор существующих шести вариантов и отдельное свободное уточнение.
- Что против него работало (`opponent_what_worked`).
- На чём он ошибался (`opponent_errors`).
- «Приложение помогло тебе в этом матче?» — обязательный явный Да / Нет.

Текстовые поля необязательны по отдельности. Для генерации достаточно хотя бы одного непустого текста из своих ошибок, эмоций, уточнения стиля, что работало или ошибок соперника. Только выбранные чипы не заменяют текстовое наблюдение. Пробелы не считаются текстом. Модель не заполняет отсутствующие наблюдения выдуманными фактами.

Готовый разбор сохраняет два голоса: тренер и психолог. Новые наблюдения соперника становятся источниками досье после успешного сохранения разбора. Если логин не задан, не обещать запись «В досье» конкретного человека.

Один сохранённый разбор на матч. Повтор после потери ответа открывает сохранённый результат, а не запускает повторную генерацию. Проверку наличия готового разбора выполнять до обращения к AI. Редактирования готового разбора нет.

## 7. Журнал и досье

### Журнал

Период: выбранный календарный месяц или всё время. По умолчанию текущий месяц, возможность выбрать любой месяц истории. Поиск соперника доступен независимо от периода и списка матчей; открытие досье не создаёт матч.

Список включает подготовки, активные и завершённые матчи, как текущий журнал. Статусы различаются явно: «План», «Идёт», «Без разбора», завершённый с результатом. Старые отменённые записи не удаляются; обычная статистика их не включает.

Детали: контекст и результат, исходная подготовка и план, все события с исходными отметками/комментарием и ответами AI в хронологическом порядке, разбор или действие «Разобрать матч». Старые поля событий и разбора имеют fallback. Длинные блоки раскрываются. Активный матч открывает возможность продолжить, а не пустой экран готового разбора.

Показатели за период:

- «Завершено матчей» — все `completed` в периоде по `match_date`.
- Победы / поражения — только завершённые с однозначно разобранным исходом. Старые неизвестные результаты отдельно обозначаются и не становятся поражениями.
- «Приложение помогло: X из Y · Z%» — X новых положительных ответов, Y всех новых явных ответов Да/Нет. При Y=0 — «Пока нет ответов», а не 0%.

Не смешивать прежний вопрос `advice_changed_play` с новым вопросом об общей пользе. Старый ответ можно прочитать в деталях под исходной формулировкой, но он не входит в новую долю.

Агрегаты считаются на сервере по всей истории периода независимо от размера страницы. Список имеет пагинацию, детерминированную сортировку и подгрузку. Ограничения текущих 50 строк и 5 встреч не определяют итоговую статистику.

### Досье

Идентификатор — точное сохранённое значение логина/старого имени. Отдельный экран каталога не обязателен: поиск в журнале и экран досье достаточны.

Вверху: логин, число завершённых встреч, баланс с учётом неизвестных исходов. Затем AI-сводка «Стиль / Что работает / На чём ошибается», дата актуальности и число матчей с исходными наблюдениями. Ниже — датированные исходные записи по всем встречам (счёт, стиль, уточнение, что работало, ошибки), с переходом в детали.

Сводка строится по всем доступным наблюдениям этого соперника, не только последнему разбору и не пяти последним встречам. Отсутствие разбора не является наблюдением. До первого содержательного наблюдения — пустое состояние; одна запись уже достаточна для сводки с честной пометкой малого объёма истории.

При противоречиях модель отмечает изменения по датам и неопределённость, а не механически склеивает несовместимые выводы. Исходники остаются источником истины. Каждая часть сводки содержит ссылки на `match_id` источников; API проверяет, что ссылки принадлежат выбранному сопернику.

Сводка кэшируется по логину, отпечатку всех исходных наблюдений и версии промпта. Сохранение нового разбора делает её устаревшей; следующее открытие досье/подготовки обновляет. До успеха можно показать предыдущую сводку с пометкой «Обновляется» и свежие исходники. Сбой AI не блокирует доступ к истории. Повторное открытие неизменной истории не вызывает новую генерацию.

Для большой истории допустима поэтапная сводка с покрытием всех записей, без скрытого отсечения хвоста. В предматчевый план передаётся сводка с датами/источниками и актуальные наблюдения; если сводка ещё недоступна — доступные исходники с явным ограничением объёма, без блокировки подготовки. Полный UI досье всегда имеет доступ ко всем исходным страницам.

## 8. Черновики, повторы и ошибки

На устройстве сохраняются подготовка (создание и правки), форма перехода/нового сета, финальный счёт, анкета разбора. Ключ включает версию формата, сервер подключения, тип формы и `match_id` либо отдельный идентификатор ещё не созданной подготовки. Смена подключения не подставляет чужой черновик. API-ключ не дублировать внутри черновиков.

Сохранение после изменения поля с коротким debounce и при уходе из формы. Сохраняются все поля, выборы, ревизия и идентификатор операции, но не вымышленный результат запроса. Черновик удаляется только после подтверждённого сохранения соответствующей операции или явного сброса пользователем. Просроченный статус матча не разрешает отправить старый черновик вопреки жизненному циклу.

Черновик разбора восстанавливается при открытии завершённого матча без разбора. Если разбор уже есть, отображается серверный результат и локальный черновик больше не предлагается. Черновик обновления подготовки после старта недоступен к отправке.

При ошибке: поля остаются, есть понятное сообщение рядом с действием и «Повторить». Один исчезающий тост не является единственным сообщением об ошибке. Таймаут клиента — 60 секунд; он не означает, что сервер ничего не сохранил.

В новом контракте создание/обновление подготовки, событие, завершение и разбор имеют стабильный `idempotency_key`; одинаковый повтор с тем же содержимым возвращает тот же результат. Идентификатор сохраняется в черновике при потере ответа. Изменение содержимого после сбоя требует нового идентификатора только после разрешения неопределённого исхода прежнего запроса. Одинаковый ключ с другим телом возвращает конфликт, а не прежний совет к новым наблюдениям.

Состояние новой операции доступно авторизованному клиенту через `GET /api/operations/:idempotency_key`: `pending`, `succeeded` с сохранённым результатом, `failed` с ошибкой или `not_found`. Серверная запись связывает ключ, тип операции, матч, хеш тела и результат. Зависшая операция разрешается сервером с проверкой фактических записей и защитой от поздней записи старого исполнителя; клиент не угадывает успех по истечении таймаута. Пока результат не определён, UI предлагает проверить/повторить ту же операцию, но не отправлять изменённую параллельную версию.

Защита нужна не только для событий, но и для создания/обновления подготовки и разбора. Параллельные запросы не создают дубликаты и не запускают повторную генерацию без необходимости. Старт и сохранение профиля обеспечивают повторяемость переходом состояния / PUT без необходимости нового обязательного ключа. На время отправки действие блокируется; пользователь может читать другие разделы. Поздний ответ не перебрасывает его принудительно с другого экрана, но результат сохраняется и становится доступен.

Постоянный профиль и настройки сохраняют текущие поля. Проверка подключения выполняется реальным защищённым запросом; зелёный статус не рисуется заранее. Полного offline, очереди отправки в фоне и решения проблемы VPN в эту работу не входит.

## 9. Изменения данных и API

Детали имён служебных таблиц можно уточнить при реализации, но следующие контракты и семантика обязательны.

| Область | Аддитивное изменение |
|---|---|
| Подготовка | Ревизия, nullable `match_context_snapshot` для совместимости со старыми строками и атомарное обновление того же матча только в `preparing` |
| Legacy-уточнения | Отдельные датированные записи контекста с `match_id`, полем и значением; не изменяют исходный снимок |
| События | Nullable `completed_set_result` = won/lost; явная версия/формат нового наблюдения, чтобы отличать старый контракт и отсутствие точного счёта |
| Разбор | `opponent_styles` text[] и `opponent_style_note` text; старый `opponent_style` сохраняется |
| Метрика | Новый nullable boolean `app_helpful`; старый `advice_changed_play` не переименовывается и не копируется |
| Сводка | Серверный кэш досье с логином, отпечатком источников, версией промпта, текстом, ссылками на источники и датой |
| Повторы | Серверная фиксация операций/результатов для устойчивых повторов и конфликтов содержимого |

Для новых разборов legacy `opponent_style` заполняется читаемым объединением выбранных стилей и уточнения. Старые свободные строки не принудительно разбиваются по запятым в массив. Legacy `technical_comment` и `mental_comment` заполняются соответствующими новыми текстами, в том числе пустыми, если пользователь их пропустил.

Старые клиенты могут по-прежнему отправлять один `opponent_style`, прежний вопрос `advice_changed_play` и старый payload `new_set`. Новый клиент передаёт `contract_version: 2` в подготовке, завершении, событиях и разборе; отсутствие означает legacy-контракт. Версию события/разбора сохранять вместе с записью. Для новой анкеты обязательны `app_helpful` и две оценки, но не старый вопрос. Совместимость не означает смешение семантически разных ответов.

Legacy запросы без ключа для создания подготовки, завершения и разбора продолжают приниматься. Гарантия восстановления результата по идентификатору относится к новому контракту; у legacy остаются ограничения одного активного матча и одного разбора, а существующий ключ событий остаётся обязательным. Старый старт без ревизии тоже допустим: транзакционно стартует текущую сохранённую подготовку. Новый старт передаёт её ревизию и при несовпадении требует перечитать план. Валидация нового UI (например, текстовых полей и финального счёта) не применяется задним числом к сохранённым строкам.

Предлагаемый интерфейс:

| API | Требуемое поведение |
|---|---|
| `POST /api/matches/prep` | Создание с устойчивым ключом операции, сохранением старого контракта |
| `PUT /api/matches/:id/prep` | Новая операция обновления подготовки: анкета, ревизия, ключ; атомарный результат |
| `POST /api/matches/:id/start` | Старт только сохранённой версии подготовки, разрешение конфликтов ревизии |
| `POST /api/matches/:id/events` | Поддержка нового формата завершённого сета и старого формата; строгая идемпотентность |
| `POST /api/matches/:id/finish` | Сохраняет результат; повтор сверяется с уже сохранённым результатом |
| `POST /api/matches/:id/review` | Новая версия анкеты; готовый разбор проверяется до генерации |
| `GET /api/operations/:idempotency_key` | Состояние и сохранённый результат операции нового контракта |
| `GET /api/matches` | Период и пагинация; поле `matches` в ответе сохраняется, метаданные добавляются |
| `GET /api/matches/stats` | Полные агрегаты за период с определёнными выше знаменателями |
| `GET /api/opponents?query=…` | Поиск сохранённых логинов/имён с пагинацией |
| `GET /api/opponents/dossier?opponent_name=…` | Полные счётчики, состояние кэша и доступная сводка, исходные записи с пагинацией |
| `POST /api/opponents/dossier/refresh` | Идемпотентное обновление устаревшей сводки по текущим источникам; без изменения исходников |

Существующие `GET /api/opponents/history`, чтение активного матча/деталей, профиль, отмена, legacy обновление точного счёта и уточнение стиля не удаляются. Новый UI не зависит от лимита старого opponent-history endpoint. Досье и новые endpoints имеют ту же авторизацию; браузер не обращается в Supabase напрямую.

## 10. Миграции и сохранность

1. До применения миграций — резервная копия затрагиваемых таблиц и проверяемый способ восстановления.
2. Миграции только добавляют поля/таблицы/ограничения, совместимые со старыми данными. Не удаляют и не пересоздают матчи, не меняют идентификаторы и внешние ключи.
3. Старые планы, профили-снимки, события, тексты разборов, ответы о пользе и результаты не переписываются массово. Поля новых ответов для старых записей остаются неизвестными, а не получают подставленные значения.
4. Не выполнять удаление Oura-столбцов или другие отложенные разрушительные миграции в составе редизайна.
5. Порядок выпуска: резервная копия → аддитивные миграции → совместимый backend → новый frontend. Старый frontend должен оставаться работоспособным при откате UI.
6. На копии существующих данных сравнить до/после количество строк, множества идентификаторов, связи и значения исходных полей. Прогнать сценарии чтения старого плана, события и разбора. Любое отличие исходных данных требует объяснения до выпуска.
7. Смена схемы и выкладка выполняются как отдельный этап реализации, с реальной проверкой среды; этот документ сам по себе ничего не разворачивает.

## 11. Требования к интерфейсу

- Светлая тема по умолчанию; ночная включается вручную в настройках и хранится на устройстве.
- Выбранные чипы в обеих темах читаемы: для текста на тёмной плашке использовать светлый контрастный токен, а не цвет фона страницы.
- Ключевые touch targets не меньше 44×44, чипы обычно 48 px и выше; две строки не уменьшают шрифт до нечитаемого.
- Поля ввода не меньше 16 px. Ключевые инструкции на корте крупнее служебных меток. Длинные логины, ответы AI и увеличенный системный текст не перекрывают действия.
- Кнопка совета постоянно доступна; раскрытие комментария и экранная клавиатура не закрывают её без доступного способа вернуться.
- Чипы имеют доступное выбранное состояние; оценки — видимые числа и подписи шкалы, а не только окрашенные пустые прямоугольники. Кнопки и переключатель темы имеют доступные имена.
- Учитывать safe areas, маленькую ширину от 320 px, ориентацию, прокрутку и `prefers-reduced-motion`. На широких экранах — ограниченная центральная колонка.
- Нет вымышленных состояний вроде «риск будет понижен» до получения плана. Загрузка описывает действие сервиса, а не обещает ещё неизвестный вывод.
- Иконки и декоративные детали могут отличаться от глифов референса ради понятности. Сохранить узнаваемые разделы и визуальную иерархию.

## 12. Критерии приёмки

### Данные и сценарии

- [ ] Миграции на копии сохраняют все исходные строки, IDs, связи и значения; новые поля не выдают отсутствующие сведения за ответы.
- [ ] Анкета редактируется с пересборкой в том же `match_id` только до старта; сбой не портит предыдущий план.
- [ ] Конкурирующий старт и обновление подготовки не меняют анкету уже начатого матча.
- [ ] Legacy-уточнение стиля отображается отдельно от исходного снимка; старые запросы без новых ключей/ревизий продолжают работать.
- [ ] После перезапуска `preparing` возвращает к плану, `in_progress` — к матчу; ошибка API не маскируется под отсутствие матча.
- [ ] Переход сохраняет положение в текущем сете, стадию и выбранные наблюдения без фиктивного точного счёта.
- [ ] Новый сет сохраняет результат законченного сета и запас сил; выдаёт план следующего без выдуманного номера сета.
- [ ] Итоговый счёт вводится колёсами; завершение можно сохранить отдельно от разбора.
- [ ] Разбор доступен позже, требует двух оценок, нового Да/Нет и одного текстового наблюдения; пустые остальные поля допустимы.
- [ ] Готовый разбор нельзя редактировать или повторно генерировать; повтор после потери ответа открывает сохранённый.
- [ ] Черновики переживают закрытие, не пересекаются между матчами/подключениями и очищаются только после подтверждённой операции или явного сброса.
- [ ] Сетевые повторы и параллельные запросы не дублируют события/подготовки/разборы; разные тела с одним ключом дают конфликт.
- [ ] Журнал открывает старые и новые планы, исходные наблюдения, все советы и разборы с правильными действиями по статусу.
- [ ] Поиск позволяет открыть досье без матча и выбрать точный старый логин при подготовке.
- [ ] Досье учитывает больше пяти встреч, показывает источники и корректно обновляется после нового разбора; ошибка сводки не скрывает историю.
- [ ] Статистика на наборе более 50 матчей верна независимо от пагинации; месяц и всё время работают; старые ответы не смешиваются с новым вопросом.
- [ ] Старые клиенты/записи поддерживаются, а новый UI не отправляет вымышленные legacy-ответы для прохождения валидации.

### Интерфейс и продукт

- [ ] На телефоне цепочка «открыть переход → выбрать проблему и контекст → отправить» укладывается в целевые 15 секунд без текстового комментария; время AI измеряется отдельно.
- [ ] Кнопка отправки не требует прокрутки; последний совет главный после возвращения в матч.
- [ ] Проверены светлая и ночная темы, выбранные чипы, клавиатура, маленький экран, длинные логины, максимальные тексты 320/700 символов и legacy-планы.
- [ ] Ошибка и восстановление не теряют ввод; незавершённая отправка не рисует фиктивный успех.
- [ ] Полевая проверка после выпуска: в первом реальном матче прочитать совет и ответить на вопрос об общей пользе. До такой проверки не заявлять доказанную пользу продукта.

Проверки реализации: целевые unit/API тесты на новые контракты, жизненный цикл, миграции и агрегаты; существующий набор `python3 -m pytest -q`; проверки Python и JavaScript; ручная браузерная проверка перечисленных сценариев. Тесты разметки обновляются по новому поведению, а не только переименованием селекторов.

## 13. За рамками

Новый фреймворк/сборка, multi-user, полный offline, голос, автоматический счёт по очкам, незавершённые по времени матчи, редактирование готового разбора, изменение подготовки после старта, автоматическое объединение соперников, экран статистических паттернов, решение VPN и выбор новой AI-модели не входят в эту работу.
