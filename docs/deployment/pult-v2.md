# Выпуск «Теннис · Пульт» v2

Реализация подготовлена в ветке `codex/tennis-pult-v2`. Производственная база в ходе разработки не изменялась. Проверки используют подменённые сервисы и отдельный PostgreSQL WASM (PGlite).

## До обновления

1. На время снимка и миграции прекратить записи из старого клиента. Сохранить текущие версии frontend/backend для отката.
2. Сделать полный резервный снимок Supabase средствами проекта либо `pg_dump` с проверенным подключением. Снимок должен включать схему, данные, ограничения, функции и права. Хранить вне репозитория: внутри есть личные анкеты и медицинский контекст.
3. Восстановить снимок в отдельную тестовую базу и убедиться, что открываются существующие матчи, планы, события, разборы и профиль. Зафиксировать набор ID и значения всех старых столбцов таблиц `matches`, `match_prep`, `match_events`, `match_reviews`, `player_profile`, включая старые дополнительные столбцы.
4. Проверить, что установлены необходимые прежние добавочные миграции: обе миграции `20260730_*`, `20260805_mental_pattern.sql`, `20260907_changeover_observations.sql`, `20260907_match_review_opponent.sql`, `20260907_session_type_duration.sql`. Для старых схем проверить также `20260729_dual_persona_reviews.sql`.

**Не запускать все файлы миграций по маске:** `20260907_remove_oura.sql` удаляет старые значения и не входит в этот выпуск. Не пересоздавать рабочие таблицы через `schema.sql`.

## Порядок выпуска

1. Применить только `supabase/migrations/20260908_pult_v2.sql` сначала на восстановленной копии. Запускать весь файл одной транзакцией (`BEGIN` / `COMMIT`); при ошибке — `ROLLBACK`.
2. Сравнить копию до/после: каждый прежний ID существует, все прежние значения совпадают, количества строк старых таблиц совпадают. Новые столбцы допустимы; у старых разборов `app_helpful` остаётся NULL. Повторное применение миграции не должно менять историю.
3. Только после успешного сравнения применить тот же файл одной транзакцией на рабочей базе и повторить сравнение до возобновления записей.
4. Обновить backend, включающий `pult.py`, `db.py`, `gpt.py`, `app.py`. Публичные новые маршруты защищены тем же API-ключом. RPC доступны только service_role; браузер не получает ключ Supabase.
5. Проверить `/api/health`, авторизованное чтение старого матча с `contract_version=2`, старый запрос без версии и OPTIONS для новых маршрутов с разрешённым `Origin`.
6. Затем опубликовать содержимое `docs/` на GitHub Pages. Новый frontend требует новую миграцию и backend. Обновление интерфейса первым недопустимо.
7. На реальном устройстве проверить старую историю, редактирование подготовки в том же матче, старт, переход, новый сет, завершение колёсами, отложенный разбор, досье и восстановление черновика. Проверить реальный ответ AI и подключение с используемым VPN отдельно: локальные тесты их не подтверждают.

Для новой базы: сначала `supabase/schema.sql`, затем `20260908_pult_v2.sql`. Базовый schema.sql описывает прежний контракт; новый слой подключается миграцией.

## Откат

Вернуть предыдущие frontend/backend. Добавочные столбцы и таблицы оставить: их удаление потеряет новые записи. Не восстанавливать старый снимок поверх работающей базы после новых матчей — сначала сохранить и согласовать перенос данных, созданных после выпуска.

## Проверки разработки

```sh
python3 -m pytest -q
python3 -m py_compile app.py db.py gpt.py pult.py
node --check docs/app.js
npm install --ignore-scripts
npm test
```

Node-зависимости нужны только тестам, сборки приложения нет. Их прямые версии закреплены в package.json; lock-файл пока отсутствует (загрузка отклонена). При первом разрешённом обновлении зависимостей сохранить package-lock.json.

Для ручной проверки запустить в двух терминалах из корня проекта:

```sh
python3 -m http.server 8770 --bind 127.0.0.1
```

```sh
python3 tests/pult_preview.py
```

Открыть `http://127.0.0.1:8770/docs/`, указать API `http://127.0.0.1:8771` и тестовый ключ `preview-key`. Это только вымышленные данные в памяти; после перезапуска тестового API они сбрасываются. Ни Supabase, ни OpenAI не вызываются.
